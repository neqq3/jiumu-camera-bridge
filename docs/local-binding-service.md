# 本地绑定实验服务

已实现独立 Node.js HTTP 引导和加密 TCP 绑定服务；服务不依赖安卓、厂商账号或 SD 卡，不主动连接厂商。2026-10-11 已在单台 A907-J / 21.120.101.42 上完成重置后的本地配网、设密、新会话认证、音视频取流和 Frigate 恢复，随后一次按键关机/开机也自动恢复。**这是研究部署，不是已交付的用户安装流程；完整外网隔离和完全移除供电后的冷启动仍未验证。** 不应在安装桥接时自动开启，也没有接入 HAOS 正式向导。

## 已实现

- `POST /node/query`：核对单个来源 IPv4、预先选定的真实设备 ID，以及设备提交的加密证明；返回本地 TCP 地址和持久化 token。HTTP 返回明确长度并关闭连接，响应尺寸低于固件的缓冲区上限。
- TCP：小端 8 字节头、AES-256-CBC / PKCS#7；支持拆包与连续报文，密文上限 8192 字节。来源地址、设备 ID、设备 code、固件版本、本地 token 均核对后才接受登记。
- 默认 `observe`：处理登记、心跳和现有 shadow 版本，不发送密码、P2P 身份或设备功能配置。引导响应仍可能使固件保存本地服务器地址/token，不能称为完全无写入的真机观察。
- 显式 `bind-once` 加 `arm: true`：还必须匹配预先配入摄像头的非空本地 uid；发送事件 2 的短 challenge，收到 `allow` 和相同 challenge 的事件 3 请求后才发送一次密码。
- 首先原子保存新密码和“已尝试发送”状态，再写 socket。断线、重复请求、服务重启均不会自动再改密。发送成功、shadow 请求均不标记为“摄像头已接受”。
- 可显式开启固件专用的 `allowP2pBootstrap`，在绑定后通过 shadow 事件 4 下发经过离线校验的 AP 引导参数，识别事件 7 的系统 shadow 确认。默认不发送；确认也不等于媒体就绪。
- `configure-alarm-upload` 是独立研究模式：只下发 `desired.isReport`，不与设密或 P2P 初始化组合。实现及模拟测试完成，尚未用于真机；具体限制见下文。
- 固定缓冲区、连接数量限制、握手/分片/HTTP 绝对超时、慢客户端输出限制；认证后保留心跳连接，使用空闲超时及每个时间窗口的字节/报文上限，不强制每五分钟断开。不支持任意命令转发、OTA 或工厂事件。
- 摄像头重启可能留下未关闭的 TCP 连接；允许一个待认证连接进入，且仅在完整登记认证通过后替换旧会话。错误 token 或空闲连接不能踢掉现有会话。

这套旧协议使用固定的协议密钥，来源 IP、设备 ID 和加密字段不能提供现代双向认证，也不防同网段攻击者冒充。服务仅用于用户自己的单台摄像头，应限制在可信实验网络，不能暴露到公网。

## 启动配置

入口是 `jiumu_bridge/local-binding.cjs`，只接受一个配置文件路径，不通过命令行传密码。以下值为示例，摄像头 ID 需来自本地发现/状态信息；这里的 `did` 是 HTTP 引导用的真实设备 ID，不是可能不同的 HLP / P2P DID。

```json
{
  "mode": "observe",
  "listen": "127.0.0.1",
  "advertiseIp": "127.0.0.1",
  "httpPort": 18084,
  "tcpPort": 18085,
  "materialFile": "protocol-material.json",
  "dataDir": "state",
  "learnCodeFromBootstrap": true,
  "target": {
    "sourceIp": "127.0.0.1",
    "did": "REPLACE-REAL-DEVICE-ID",
    "firmware": "21.120.101.42",
    "uid": "REPLACE-LOCAL-OWNER"
  }
}
```

`learnCodeFromBootstrap` 允许从已选定摄像头自己的合法引导请求中取得 code，并保存在本地；首次保存后拒绝替换，不要求用户去 APP 提取。也可预先配置 `target.code`。这不是发现任意摄像头后自动接管的服务：仍需先确认单台设备身份和实际 LAN IP。

协议材料文件包含 `profile: "bk7252n-21.120.101.42"`、`keyHex`（64 位十六进制）、`ivHex`（32 位十六进制）。本实验由已核验哈希的用户固件生成，文件不随源码发布。公开安装包的协议材料交付方式尚未完成；目前仍是研究入口，不能宣称普通用户已能一键无账号接入。

首次 AP 配网会清除 `did` / `license` / `initString`，仅设密码不能启动 LAN P2P。本次在材料文件加入 `p2pBootstrap`（`did`、`license`、`address`、`version`），并在服务配置同时启用 `mode: "bind-once"`、`arm: true`、`allowP2pBootstrap: true`。参数来自固件自身的共享 AP 默认值，**不是新签发的唯一设备云身份**。连接必须限定目标 IP，再核对真实设备 ID；多摄像头、广播重名、厂商共存尚未验证。不能把共享默认值当作生产环境的唯一身份或用于恢复厂商服务。

```sh
node jiumu_bridge/local-binding.cjs /path/to/private/binding.json
node --test --test-timeout=20000 scripts/binding.test.cjs
```

默认仅回环监听。LAN 试验需要显式 `allowLan: true`、绑定具体 LAN 地址、正确的单摄像头 `sourceIp` 和可达 `advertiseIp`；拒绝 `0.0.0.0` 和公网地址。配置和状态仅在本地保存，未加密；Linux 创建权限为文件 0600 / 目录 0700，Windows 必须靠目录 ACL 控制访问。日志只含事件名、计数、监听信息，以及白名单内的断线原因、时长、登记原因和电源状态；不含请求正文、ID、uid、token 或密码。电源状态会报告电量、是否充电及有效电压值，心跳日志最多每 15 秒一次；登记原因来自固件字段，不能直接当作硬件重启原因。

状态目录不能随意清空。Linux 使用内核 `flock` 锁：即使工作进程被强制终止，锁也随进程退出释放，Docker 可以自动恢复；`binding.guard` 文件需要保留，不能通过删除它解决锁冲突。镜像启动依赖 `flock`，缺失时拒绝运行。旧版本留下的 `binding.lock` 不会被自动删除：升级前正常停止旧服务；若旧服务已经崩溃，需先确认没有旧进程使用该目录，再处理旧标记，保留 `binding-state.json`。非 Linux 仍使用旧标记机制，不承诺异常终止自动恢复。存在 `delivery-attempted` 时应先使用已保存的密码验证摄像头，不能靠删除状态重试改密。

## 仅配置自动告警上报（研究功能）

这不是向任意 LAN 摄像头直接发送 CGI 的工具。前提是已选定的摄像头能向本地服务完成普通业务登记（事件 1）；目前官方账号模式的摄像头仍连接厂商业务服务器，**仅启动此模式不会使其改向或生效**。本服务尚不支持 SD 工厂模式的事件 15 登记，也不自动修改 DNS、路由、摄像头服务器地址或身份。此前 HTTP 引导可能写入本地地址/token 的限制仍然适用。

在既有私有配置中采用以下片段，保留正确的 `target`、协议材料和状态目录。示例版本 12 仅供说明，实际必须先从当前连接的 `lastShadowVersion` 取得版本，再明确选择更大的值（最大 2147483647）；不能直接套用示例。

```json
{
  "mode": "configure-alarm-upload",
  "arm": true,
  "alarmUpload": {"enabled": false, "version": 12}
}
```

只允许固件 `21.120.101.42`，并核对来源、真实设备 ID、code、token、固件及所有者 uid。拒绝同时启用 `allowP2pBootstrap`，也拒绝在 `alarmUpload` 中加入任意其他字段。收到较旧版本请求后发送事件 4，内容仅为 `{"version":12,"desired":{"isReport":0}}`，没有 `alarm`、录像模式或 P2P 参数。

同一连接最多发送一次；设备报告相同或更高版本时只回复其版本，不重写，也不推断开关当前值。重新连接后，只有仍报告较旧版本才会重试。状态中的 `deliveries` 只计发送次数，事件 7 只计确认回包，`deviceStateVerified` 始终为 false。`version_matches_unverified` / `newer_version_unverified` 均不代表隐私设置生效。相同版本也可能存在不同字段值，必须独立读取。

真机验证顺序：

1. 保存独立 command3/8 读取结果、SD 录像模式及当前 shadow 版本。先确认业务改向方案和恢复材料；不能靠删除状态目录重新试绑定。
2. 下发 `isReport=0`，再用独立 command8 确认 `pirPushSwitch=0`。不要用 command9 的成功应答代替，固件该应答读取了另一个字段。
3. 若此前关过检测，在读回确认上报关闭后，再单独恢复 `humanDetection=1`。保留灵敏度、睡眠及录像设置，按需单独验证事件录像模式；不要把未知值改成默认值。
4. 完全退出 SDK/P2P 预览连接，再触发运动、检查 SD 新事件文件和业务事件 9/10/11/12。当前 HLP 拉流会抑制相机 SD 录像，仅停止播放但保留会话不够；因此这也尚不是 Frigate 与 SD 同时录像的方案。
5. 重启后独立读回，再重复检测、录像及上传检查。厂商配置同步可能重新覆盖 `isReport`；已开始的告警也不保证立即终止。

恢复上报需使用明确的 `enabled:true` 和比设备当前版本更高的新版本，再独立读回，不能复用旧版本冒充恢复成功。恢复先前检测设置是另一项操作。此开关只门控新自动告警的元数据、图片和视频；不禁止正常 P2P 预览或业务服务器主动直播，不能标为“所有媒体不出网”。详见 [隐私开关研究](research/privacy-controls.md)。

离线独立 AES/TCP 模拟客户端已覆盖最小下发、错误所有者、无关/重复确认、旧/同/新版本、服务重启、恢复上报及凭据文件保持不变。模拟客户端不运行原固件，不能代替设备接受、NVS 写入、重启和实体卡验证。

## 仅替换 SDK 服务器地址（研究功能）

`configure-p2p-endpoint` 用于已绑定设备向本地业务服务完成登记之后，单独下发 `desired.p2p.address`。它不发送 `did`、`license`、绑定 challenge 或设备密码，也不修改检测、录像和告警字段。此功能与无账号首次绑定分开；不能用共享 AP 默认身份覆盖官方账号设备。

```json
{
  "mode": "configure-p2p-endpoint",
  "arm": true,
  "p2pEndpoint": {"address": "REPLACE-VALID-PRIVATE-DAS-STRING", "version": 12}
}
```

示例不能直接运行：地址必须是经过校验的私有 DAS 参数，版本必须大于观察到的 `lastShadowVersion`。要求精确固件 `21.120.101.42` 和预先核对的所有者 uid，拒绝额外字段及混用首次绑定、告警配置。DAS 内的发现组、密钥和其他字段应保持不变，只替换服务器列表并按固件算法重算校验。不要把加密地址当作可公开的普通 URL。

同一连接只向较旧版本发送一次；相同或较新版本只回版本号。匹配的事件 7 仅记为 `acknowledged_unverified`，`deviceStateVerified` 仍为 false。独立读取、实际取流和重启验证才是生效证据。回退地址也必须显式使用原值及更高版本，不能复用旧版本或清空状态目录。

**业务连接改向仍是前置条件。** HTTP `/node/query` 的业务服务器与 DAS 中 SDK TCP 65527 地址是两条不同路径。该固件会缓存业务 IP/token，业务 TCP 重试会继续使用内存中的旧地址；失败路径虽会清除部分持久配置，不能据此认为 DNS 一改就立即生效。实际切换可能需要在准备好单设备规则后重启摄像头。HTTP 引导还会改变业务地址/token，所以只关闭 DNS 规则不一定能完全恢复，需要单独验证业务端点回退。

已在一台原官方账号模式的 A907-J / `21.120.101.42` 验证地址改向：保留原账号绑定、DID 和密码，只改 DAS 服务器字段及校验。目标摄像头先向本地业务服务登记，再接受地址策略。NAS 包头观察确认 SDK 的 TCP 65527 已指向本地地址，收到立即 RST；媒体不需要实现厂商中继服务器即可继续通过原 LAN 客户端取得。

单摄像头 IPv4 外网阻断保持启用时，改向后的五分钟窗口 60 次音视频采样均正常、没有新增重连；相应网关 LAN 侧观察没有公网数据包或 IPv6 包，内核丢包为零。新 Frigate 录像包含 H.264/AAC 并实际解码通过。撤掉地址下发策略、改回 `observe` 后，用户用电源键关机至灯灭，网络探测和媒体均离线；再开机自动报告原新版本、连接本地服务并恢复原凭据拉流，新的三段录像同样通过检查。服务没有在这次开机时补发地址策略。

这证明该台设备的本地接管和一次电源键关机开机恢复，不等于断开内置电池的冷启动或长期稳定性通过。TCP 可达、shadow 确认和 LAN 取流成功，都不能单独证明没有其他厂商连接。保留单摄像头外网控制作为实验边界；尚未验证关闭这层限制后是否仍无外联，不能将此模式标为无需网络限制的完整隐私保证。未使用 SD 卡、未刷机；账号接入基线与本地接管仍应在产品中作为不同模式展示。

## Docker 实验入口

`binding.Dockerfile` 只复制该服务所需的原创 JS 模块。`compose.binding-lab.yaml` 提供显式 profile，默认不随媒体桥接启动。先准备 `data/binding-config/binding.json` 和协议材料，配置 `dataDir: "/data"`。初始仍用回环地址测试：

```sh
docker compose -f compose.binding-lab.yaml --profile binding-lab build
docker compose -f compose.binding-lab.yaml --profile binding-lab up
```

此模板使用 Linux host 网络以保留来源 IP；未在 Docker Desktop 或 HAOS Supervisor 验证。镜像以 UID/GID 1000 运行，挂载配置须对其可读，状态目录须对其可写；保持配置 0600、目录 0700，并匹配实际所有者。默认仅监听高位回环端口，不修改主机 DNS、防火墙或路由。真机引导访问 HTTP 80，DNS A 记录不能改变端口；需要另行选择无冲突服务地址及部署方式。本模板删除了所有 capabilities，若实际部署要监听 80，需核对宿主内核的非特权端口设置或只增加必要的 `NET_BIND_SERVICE`，不能因此启用 privileged。

显式启用实验 profile 后，容器使用 `init: true`、`restart: unless-stopped` 和独立 `/tmp`。健康检查核对监听状态及 30 秒内更新的状态文件，不会把健康自动等同于摄像头在线，也不会重新设密。已在 Linux 真机部署强制终止单个绑定工作进程，确认 Docker 自动重启、恢复 healthy，且密码、token 和首次下发时间不变。宿主机整机重启尚未测试；启动与断电验证清单见 [恢复验证](recovery.md)。

认证前有绝对截止时间；认证后 `sessionMs`（默认 300000）用作流量预算窗口，每窗口最多 128 个报文 / 131072 字节，不再表示有效连接的最大寿命。`idleMs` 默认 90000，完整分片与绑定 challenge 仍有各自绝对期限。固件正常心跳约 60 秒；短于此值的空闲期限会人为造成掉线，不适合实际部署。此前五分钟硬断开在真机上伴随一次媒体中断，已移除，但不能据此认为所有断流来源都已解决。

本次 NAS 使用专用 IPvlan L2 地址，镜像基于本地已有 Node/媒体运行时构建，非 root、只读根文件系统、无 capabilities。IPvlan 默认隔离宿主与容器之间的直接访问，不能把这种地址直接假定为同机 Frigate 可访问的视频出口；实测媒体桥接保留 host 网络及原 RTSP 端口。

## 验证与真机门槛

本机测试使用独立编码的模拟客户端，覆盖 HTTP/TCP 正常往返、错误身份、拆包/粘包、畸形输入、来源限制、单次绑定、存储故障、重启、端口冲突与退出清理。它不是固件仿真器，也不能证明真实摄像头已接受响应。

真机前按 [单设备路由方案](router-routing.md) 确认设备 LAN MAC/IP、服务地址/HTTP 80、规则备份与回程路径。先用观察模式核对真实引导/登记，再启用单次绑定。必须先保存 Wi-Fi 再设密码：分析到的初始 AP 配网流程会恢复部分默认配置。

收到绑定响应后，仍需分别验证 HLP 认证、实际图像解码、桥接 RTSP、Frigate、摄像头断电重启与 WAN 隔离。厂商共存模式不应使用本地改密，见 [模式选择](connection-modes.md)。

## 单台真机结果

1. 初始 AP 中读取真实设备身份、station MAC 和版本，使用本地生成的所有者编号下发 Wi-Fi。测试中的安卓设备只充当临时 Wi-Fi/UDP 适配器，没有运行厂商 APP；手机或桌面配网助手尚待产品化。
2. 配网 ACK 后保持会话：固件先回复，再等待约 1 秒读取配置。立即关闭会话曾导致“返回成功但未入网”；保持 25 秒的实验成功入网。
3. 路由器只对目标 station 地址配置静态租约、DNS 和 IPv4 WAN 限制。摄像头真实连接本地 HTTP/TCP 服务，完成 code/token/uid 检查、challenge 和单次密码下发。
4. 首次 LAN P2P 参数为空；明确启用上述 AP 引导参数后，收到系统 shadow ACK。之后等待 SDK 初始化，并用新密码建立独立媒体会话，不能以 ACK 代替此步骤。
5. NAS 主机 15 秒测试取得 119 个视频帧、132 个音频帧，真实设备身份匹配，非法包和丢弃计数均为 0；另一连接实际解码 30 帧 640×480 JPEG。现有桥接使用新凭据后，Frigate 再次取得实时画面。
6. WAN 限制下还发现 P2P TCP 阻塞和客户端遗漏累计确认两处问题，处理过程见 [协议研究](research/protocol.md)。修复后、重启前的三分钟采样持续收帧且未重连；软件重启后使用同一密码恢复，但启动阶段仍发生一次自动重连，之后恢复取流。仍需后续冷启动和长期验证。
