# 选择接入与联网方式

接入方式由用户选择。首次取得设备凭据与摄像头日常是否访问厂商，是两个独立问题。以下是产品方向及验证边界，**当前 Web UI 仍只提供已绑定设备的账号导入；没有自动配置路由器或可用的无账号绑定按钮。**

| 方式 | 首次接入 | 日常厂商访问 | 路由器要求 | 当前状态 |
| --- | --- | --- | --- | --- |
| 厂商 APP 与 HA / Frigate 共存 | APP 完成首次绑定，桥接登录账号自动导入设备凭据 | 保留 | 不需要域名重定向或外网封锁 | 账号导入与独立取流已验证；APP 与桥接同时预览、重连竞争尚待专项验证 |
| 账号辅助，之后仅本地使用 | 同上，先确认本地画面正常 | 用户选择后，单独阻断摄像头外网 | 单设备访问控制，保留 LAN 通信 | 外网隔离后的持续运行和冷启动待验证 |
| 无账号本地绑定 | 本地配 Wi-Fi，由本地绑定服务建立设备密码 | 目标为不联系厂商 | 单设备 DNS 配置 / 必要时定向 NAT，并隔离外网 | 单台真机已完成绑定、LAN 音视频和 Frigate；完整隔离、冷启动和用户向导待验证 |

三种方式都以同一局域网桥接输出 RTSP，交给 Frigate 或 HA。SD 工厂测试入口仅作为研究候选，不成为普通用户安装要求；运行桥接不需要安卓工控机。

## 厂商共存

保留设备在厂商的账号归属和原设备密码，桥接读取合法凭据后独立取流，不向设备发送本地替代绑定响应。保留厂商 APP 的联网条件，同时把画面交给 HA / Frigate。

保留联网条件不等于已经证明双客户端可长期同时观看。应检查 APP 开关预览、远程预览、桥接重连和设备密码变化时是否相互影响。厂商固件可能继续发送设备状态或媒体，具体依其功能及设置而定；此方式不宣称摄像头离云。

## 账号辅助后隔离

先导入并验证局域网取流，再由用户选择隔离摄像头外网。桥接的账号登录请求与摄像头的网络流量分别处理，不把全屋或运行 HA 的主机一起封锁。

隔离后厂商远程预览、推送或云录像可能不可用。同一 LAN 内原 APP 是否仍能使用也要实测，不能保证其登录及设备列表在无云时正常。已有设备凭据可供桥接启动，但冷启动、时间同步、凭据有效性和固件是否强制云在线仍待验证。

## 无账号本地绑定

固件包含 HTTP 服务器查询和独立 TCP 绑定协议。当前分析支持尝试把自有摄像头引向本地服务，再保存自建设备密码，详见 [协议研究](research/protocol.md)。仅修改 DNS 不会自动实现绑定，必须有正确实现并验证过的本地服务。

[本地绑定实验服务](local-binding-service.md) 已提供默认观察模式、限定单设备的绑定往返、先保存后发送的单次改密，以及独立 Docker 实验入口。后续真机已用新密码取得媒体并恢复 Frigate，但共享 AP 引导参数、首次配网助手和协议材料交付仍需产品化，尚不能作为普通用户的一键安装流程。

普通 Docker / HAOS 加载项无法单凭一个选项改变外部路由器的 DNS 和转发路径。向导应展示具体设备、所需规则、验证结果和移除方法，由用户选择是否执行；没有完成对应验证的模式应显示“实验中”，不展示已启用标记。

## 模式切换

| 切换 | 必须处理的事项 |
| --- | --- |
| 共存 → 账号辅助后隔离 | 保持设备密码，保存局域网连接验证结果，再添加仅该设备的外网限制，进行断电重连测试 |
| 账号辅助后隔离 → 共存 | 只移除本项目针对该设备增加的隔离规则；检查厂商访问及凭据是否仍有效 |
| 共存 / 隔离 → 无账号本地绑定 | 可能改变设备密码与绑定状态；保存已有本地配置，明确原 APP 可能失效，完成恢复方案后再实施 |
| 无账号本地绑定 → 共存 | 不能承诺仅删除 DNS 规则即可恢复；可能需要 APP 重新绑定、重新导入凭据并调整规则 |

实现时应分别记录“用户选择的方式”“路由器规则是否已确认”“认证和视频是否通过”“断外网冷启动是否通过”。一个选择开关不能替代这些验证，也不能自动给出“隐私保护已生效”的结论。

路由器配置设计见 [单设备路由方案](router-routing.md)，数据去向见 [隐私说明](privacy.md)。
