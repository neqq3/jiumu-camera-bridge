# 配置完成后的隐私开关研究

2026-10-12，范围仅为九目智联 1.0.12 与本次 A907-J / 21.120.101.42 固件。以下包含离线调用链分析和本机开关写入、独立读回验证；重启保存和全部媒体停止外发尚未验证。不能外推到所有 A9 摄像头。

账号登录、选择设备、局域网音视频与稳定恢复仍是产品基线。以下功能是可选研究，不要求用户修改路由器、购买无线网卡、蓝牙或 SD 卡才能使用基线。

## 已确认的区别

### 检测是在本地还是云端

已追踪的运动告警在摄像头本地运行：图像线程 `0x39474` 在采集 JPEG 后，将帧字节数传给 `0x39af8` (`processMotionDetection`)。该函数保存前次值，计算绝对变化及比例，按灵敏度阈值、时间表和告警间隔决定是否触发。调用点 `0x3957c` 与比较/计算指令 `0x39b22..0x39b2e` 已用 Capstone 复核。这条检测不需要先上传实时画面给服务器。

随后才是独立的告警发送链：本地触发 → 告警元数据 → JPEG 图片 → 可选视频/音频。是否进入发送链还受绑定、上报开关及当前预览会话等条件限制。因而“本地检测”不等于“检测图片不会上传”。

这条已定位的算法是简化的画面变化判据，不是已证实的人体/人脸模型。`humanDetection` 在本固件中控制的是 `alarmEnable`；APP 同时包含其他机型的 `HumanoidDetection` 等字段，不能只凭名字认定本机运行 AI 人形识别。厂商服务器收到图片后是否另外识别、筛选或保存，当前只有 APP/固件材料，不能确定服务器内部处理。

### 开关的覆盖范围

| 操作 | 此固件实际处理 | 能否保证全部画面不外发 |
| --- | --- | --- |
| 关闭摄像头运动告警检测 | 本地 `humanDetection=0` 保存为 `alarmEnable`，开机读取；门控已发现的图像运动与唤醒告警触发 | 不能；保留预览等独立路径，且需真机持久化验证 |
| 关闭告警视频 | `pirPushSwitchVideo=0` 保存为 `pushStream`，开机读取 | 不能；检查发生在告警 JSON、JPEG 图片发送之后 |
| 关闭“推送”参数 | 本地 `pirPushSwitch` 写入命令解析该字段后，没有更新对应状态；成功应答还读了别的字段 | 不能当成关闭成功 |
| 设云录像时长为零 | `CloudVideoDuration=0` 被改成 5 | 不能用于关闭上传 |
| 业务配置 `isReport=0` | shadow 路径保存并门控新告警的元数据、图片和视频链 | 不阻止其他直播路径；不是已支持的通用本地 CGI 操作 |
| 手机通知暂停、APP 缩略图显示设置 | APP 或账号设置 | 不能证明摄像头停止发送内容 |

APP 的云录像页面按设备能力走不同实现：低功耗分支设置本地告警视频字段；另一分支请求账号云接口。不能只凭 UI 文案或同一 APP 的其他设备实现推断本机行为。

本地命令由已认证的摄像头协议承载，不是已发现的相机 HTTP 管理页面。APP 的成功判据会直接更新缓存；真正执行、落盘及重启保留需分别读取验证，不能以一次“成功”响应替代。

## 持久化与验证边界

本机已通过认证后的局域网命令，逐项把 `humanDetection`、`pirPushSwitchVideo` 从 1 改为 0，每步均重新查询状态确认。灵敏度、休眠参数、告警视频时长未变，`pirPushSwitch` 仍为 1。写入前原值已私下保存，测试后桥接音视频与 Frigate 取流恢复。此操作关闭摄像头自身运动告警及告警视频，会影响官方 APP 的相应告警功能；不关闭 Frigate 自己的本地检测。

后续 SD 调用链核验确认：`humanDetection=0` 也会抑制摄像头自身的运动事件卡录像，不能标为“仅关闭云上传”。持续录像不受这一特定字段门控，但仍受客户端会话等条件限制。详见 [SD 配置与录像](sd-card.md)。

测试使用短暂暂停桥接的独立控制会话。并发控制查询曾超时，并在同一时段观察到取流重连；尚不能确定设备支持的并发会话上限。主动暂停与失败均保留在稳定性记录中，本次观察不能当作未经干预的连续稳定性通过。

静态分析发现 `alarmEnable` 和 `pushStream` 都有非易失存储写入与开机读回。写入路径没有把存储失败反馈到正常命令结果，因此目前只能称为“存在持久化实现”，不能称为“本机重启实测通过”。厂商后续配置同步也可能覆盖相关值。

自动告警链先发元数据，再发 JPEG，随后根据视频开关决定是否继续视频。已开始发送的事件不会因为所有开关改成零立即中断。另有业务服务器控制的实时 JPEG / 音频路径及正常 P2P 预览，不受这些告警开关限制。这是代码路径证据，不代表已经观察到厂商滥用。

因此可以进一步验证并提供含义明确的“关闭摄像头自动告警”功能，**目前不能提供或宣传“不改路由器即可保证全部媒体不出网”的开关**。Frigate 自己的本地检测不依赖摄像头的运动告警字段。

## 保留检测和事件录像，只关闭自动告警上传

目标组合是 `alarmEnable=1`、`isReport=0`，SD 使用已确认的事件录像模式。固件 `0x3fc54` 的业务 shadow 响应处理器对 `desired.isReport` 单独写 RAM，并调用 `0x471e0("isReport", value)` 保存；开机函数 `0x3a03c` 读取同名值。未包含的其他 shadow 字段不随之改写。

`0x40348` 在调用事件 9 告警元数据发送之前检查 `isReport`，零值直接返回。因此这条开关门控新告警后续事件 10 图片、11/12 视频链；本地检测 `0x39af8` 和 SD 开始录像 `0x3ea88` 不读取该字段。这支持把“检测”和“上传”分开，仍需真机验证存储成功、重启和事件录像。

已为本地业务服务增加可选的 `configure-alarm-upload` 模式，只下发该字段，并提供版本限制和恢复上报操作，见 [配置与验证步骤](../local-binding-service.md)。独立模拟客户端测试通过；**本次没有部署到摄像头，也没有重新开启此前关闭的本地检测**。

下发入口仍有限制：本机的 `pirPushSwitch` CGI setter 没有真正保存 `isReport`，当前未找到等效的受支持 LAN 命令或已验证的官方账号 API。业务 shadow 要求摄像头连接我们自己的业务服务；正常官方账号模式不会因为桥接在 LAN 上就自动接受它。后续已通过单摄像头引导定向完成本地业务登记，但尚未将 `isReport` 模式作为此次地址接管的一部分下发，不能把网络改向成功等同于上报开关验证成功。SD 工厂入口使用不同登记事件，不能直接当作现成替代方案。

另一个独立限制是**当前 HLP/SDK 取流会阻止摄像头 SD 录像**。即使上报开关验证成功，也不能马上保证 Frigate 持续拉流与 SD 事件录像同时工作。业务 TCP 的事件 18 → 13/14 直播路径没有读到相同的会话互斥门控，可作为后续双录候选；尚未实现并验证。详见 [SD 录像条件](sd-card.md)。

## SD 卡配置入口是另一条可选路径

固件读取 `/sd/product_test.txt`，其内容实际按 JSON 解析。必填字段包括 `ssid`、`pwd`、`server_ip`、`server_port`、`userId`，可选字段包括 `liveVideoSwitch`、`autoWriteVuid`。解析后会进入工厂测试模式，按指定 Wi-Fi 和业务服务器地址建立连接；该模式还跳过普通业务初始化中的告警发送线程，并改变部分休眠、关机行为。

所以 SD 卡在此设备上既能存录像，也能承载配置，不能笼统说它只影响本地录像。这是固件已有的配置入口，不是重新刷写固件。当前已追踪的解析与启动路径把参数放入内存，尚未证明“插卡一次、拔卡重启后永久保留”。指定业务服务器也不等于所有 SDK/P2P 云连接都已改向。本路径尚未用实体卡验证，保留为可选研究，不是账号接入的必需品。

进一步分析发现服务器可另外下发持久参数，因此也不能反过来承诺“拔卡重启恢复原样”。热插、拔卡、重启与双录条件见 [SD 卡情景表](sd-card.md)。

## 其他看似可用的入口

对九目智联 1.0.12 又追踪了“P2P 模式”“隐私位”和设备更新接口，结果如下：

- `setP2PPreferences → setP2PMode` 最终调用手机的 `SharedPreferences.setInt`，键为账号对应的 `_p2pMode`。这条 setter 不向摄像头写配置，不能让设备停止远程服务。
- “隐私位”发送 `trans_cmd_string.cgi?cmd=2013&command=1&posturn=...`。本机 21.120.101.42 的命令分发器没有该分支；这是 APP 兼容其他机型的功能，不是本机可用的离云开关。其他机型的物理遮挡也不满足“保留 Frigate 画面”的目标。
- 已检查的 `/device/v2/update` 调用修改账号侧设备信息；`/device/update` 调用发送推送字段。未找到它们能够写本机 `desired.isReport` 或 SDK 服务地址的证据，不应猜测字段后向云端试写。
- SDK 确有 AP 模式标志，但应用在配网模式初始化时才调用它。网络模式字节的已识别写入点来自启动网络初始化，没有发现普通 CGI setter。不能把 SDK 内部函数当成现成的局域网 API，也不能通过伪装 AP 状态保证正常 LAN 下的认证与取流。

因此，本机仍没有已验证的“无 SD 卡、不改路由、不刷固件，只发一条本地命令即可关闭全部远程媒体”的交付方案。SD 指向本地服务、重写业务配置和 SDK 服务地址仍属研究路径；这些入口不能混成一个已经验证的全局开关。

账号导入之后采用单设备网络隔离，是另外一条不需要额外配件的研究路线。但本机的官方账号配置目前没有通过这条路线的验证，不能直接作为可用功能交付。IPv4 规则也不能自动代表 IPv6 被隔离。

### 官方账号模式下的外网阻断失败

2026-10-12 经用户授权，只启用已有单摄像头 IPv4 WAN 阻断，未改 DNS、重新绑定或修改其他设备规则。随后 300 秒内，LAN 侧观察到摄像头的 65 个公网发包尝试、零公网回复；两个采集接口是重复视角，不能相加，也不能将 LAN 上的发包尝试当成已穿过 WAN。期间没有观察到 IPv6，不等于已完成 IPv6 隔离验证。

本地视频短暂恢复后再次停止。独立检查得到健康接口 HTTP 503、Frigate `camera_fps=0`，桥接失败原因为局域网发现无应答。因影响基线，仅将这条规则恢复为停用；音视频和 Frigate 自动恢复，未重启服务，随后一个新录像片段的 H.264/AAC 均解码成功。用户反馈手机流量下官方 APP 无法预览，但反馈未精确对齐规则生效窗口，而且本地取流同时失败，不能将其记为隐私功能通过。

进一步静态检查发现值得验证的等待路径：SDK 后台线程持有共享互斥锁时尝试外部 TCP 连接，连接成功后才把 socket 切成非阻塞；底层 TCP 对象初始非阻塞位为零，connect 会进入等待分支。创建本地 listen 会话和部分 SDK 会话管理也使用该锁。这说明“静默丢包拖住 SDK”有代码依据，**尚未证明就是本次实际阻塞的位置或唯一原因**。不能据此断言摄像头先把视频上传云端才允许局域网观看。

下一步应区分外联等待、监听重建和其他固件行为；若比较立即拒绝与静默丢弃，或替换业务/SDK 服务器地址，需要独立限定变更及回退范围。此轮未实施这些新变更，也未刷写固件。

### 后续本地业务与 SDK 地址接管（2026-10-13）

保留上述失败结果，后续在用户配合电源键操作的窗口中，只启用了目标摄像头的引导 DNS 定向与 IPv4 WAN 阻断。摄像头完成本地业务引导、登记，所有者与原账号匹配。新增 `configure-p2p-endpoint` 模式仅发送 `desired.p2p.address` 和更新版本，不发送 DID、license 或设备密码；地址由该设备原 DAS 参数改写服务器列表并重算校验，发现组和密钥不变。

设备确认后，NAS 观察到 TCP 65527 发往本地服务地址，SYN 与返回 RST 在同一个毫秒采样内。本地业务心跳继续应答，原桥接和 Frigate 自动恢复。独立五分钟观察 60/60 音视频正常、重连计数不变，网关 LAN 侧公网包计数零、IPv6 包零、丢包零；新录像解码通过。撤掉地址策略只保留 `observe` 后，再经确认离线的电源键关机/开机，设备自行报告更新版本并继续连接本地端点；未重新发配置，Frigate 新录像恢复。

该比较支持“用本地业务服务维持运行、把 SDK 外联改成即时本地回应”这条解决路径，不是证明所有原断流都来自同一互斥锁。测试保留单设备外网限制，未验证取消限制后的所有媒体入口。内置电池没有物理断开，不称为完整冷启动；只有单机短时和一次电源键恢复结果，不能标为 24 小时稳定。未新增 SD、安卓运行依赖或固件刷写。

## 官方 APP 外联与图片上传

九目智联 1.0.12（versionCode 119）在摄像头本地接管后，仍通过 APP 自身的公网连接发送统计和业务请求。2026-10-13 的 APP 进程内 TLS 元数据观察得到 `bpr.eye4cloud.com/burPoint/batchAdd`；特定请求的压缩 JSON 在本机解开，只保存字段名和类型，确认页面、事件、设备及版本字段，未记录标识值或认证材料。存在 IPv6 外联，摄像头的 IPv4 规则不覆盖 APP。

有效预览阶段 60 秒包头观察收到摄像头约 5.8 MB UDP 数据，12073 包、内核丢包零；另观察开始预览、11 次缩略图回调、一次普通拍照及返回列表。拍照 UI 显示保存在 APP 相册；本轮未触发已挂接的通用云文件、日志或预置位上传函数，已观察 TLS 请求没有图片/视频 MIME、multipart 或媒体头标志。只能表述为本次未发现自动转传，不能证明完整无上传。

包头过滤只覆盖采样时 APP 已拥有的端口；短命的新连接可能未被两秒一次的套接字采样发现。实际上进程内观察发现了包头窗口遗漏的业务请求，因此不能引用包头的“公网零包”来声称 APP 没有联网。TLS 观察只覆盖已验证的 Flutter 入口，socket 写入计数也不覆盖所有实现；功能和时间边界必须保留。

静态 ARM64/Blutter 名称辅助反汇编（并非 REA 直接反编译 Dart）确认：

- `DeviceProvider._snapshotChanged` (`0x2db1d60`) 更新本地 `FileImage`、清理显示缓存并刷新响应式值；这个回调中没有网络上传调用。
- `requestPresetTokenUpload` (`0x2091b08`) 使用 `/preset/temp.jpg`，取得预置位上传参数后调用 `AppCloudFile.uploadFile` (`0x1aae4ec`)。这是实际存在的图片上传路径，本轮未操作预置位，不能据此认定当前 A907 普通预览会触发。
- 该文件上传入口的其他已找到直接调用来自七牛日志上传；`AppCloudFile.upload` (`0x275cb78`) 的已找到直接调用来自头像上传。直接调用检索不覆盖所有间接分派。

初期 APP 曾停止预览并弹离线提示，相关低流量窗口未算有效直播样本；桥接也发生重连，原因未证实。单独暂停目标桥接 100 秒未令旧 APP 会话恢复；桥接随后自动启动、配置哈希不变。正常重开 APP 后才得到上述有效预览。保留全部失败和计划中断，不宣称多客户端长期稳定。观察结束后 APP 测试会话退出，Frigate 音视频恢复；未改变任何路由器或其他设备规则。

## 后续有限验证

1. 写入前备份、逐项变更及独立状态查询已完成；下一步验证重启后读回，并确认原值能够恢复。
2. 如研究 SD 配置入口，单独验证服务器改向范围、其他云连接、拔卡重启和模式退出，不把静态调用链当作已完成的一键离云功能。
3. 区分告警元数据、图片、视频、心跳和主动直播。还必须覆盖没有预览客户端时的运动场景：固件原本就在本地取流活动时抑制部分新云告警，仅在 Frigate 持续拉流时观察不到上传不构成证明。
4. 如测试环境已有外网限制，明确它只能验证设置、持久化及本地观察到的协议行为，不能用该环境“没见云流量”证明这些开关单独保证隐私。

账号接入基线已经走通；继续维护音视频与恢复，同时研究可选隐私能力。设置、重启和部署干预必须标记在观察窗口中，不删除对应中断。原 APK、固件、反汇编及私人抓包不随仓库分发。
