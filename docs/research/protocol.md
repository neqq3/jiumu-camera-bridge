# 协议与无账号配对调查

对象：九目智联 A907-J；APP 包名 `com.langxing.zhilianjiumu`，版本 1.0.12 / 119；设备报告版本 21.120.101.42。后续已从 APP 指向的官方固件目录取得并成功解包同版本 OTA 镜像，镜像内版本和 BK7252N 路径与设备信息匹配。原厂镜像及反编译输出不随仓库提供。

## 已验证的取流链路

APP 使用多协议原生 SDK；只有结合调用参数与网络包才能确认具体传输。本设备实际使用 HLP2P 类型 26。独立 Node.js 实现包含 LAN 发现、认证、ACK / 重传、有限分片重组、保活和音视频解析；发行程序不加载原厂 `.so`。

媒体帧有 32 字节头，起始标记 `55 aa 15 a8`，byte 4 是类型，offset 16 为小端 payload 长度。本设备实测类型 3 为 JPEG、类型 7 为 G.711 A-law 8 kHz。JPEG 640×480，约 10 fps，经本地 FFmpeg / go2rtc 输出 H.264 / AAC RTSP。

分片和长度都必须有上限，乱序、重复、丢包与序号回绕需要单独处理。接收成功不是解码成功；得到历史缓存帧也不是实时健康状态。验证依据包括私人抓包回放及 FFmpeg / Frigate 实际解码。

## 配网方式与状态

| 路径 | 证据 | 本机状态 |
| --- | --- | --- |
| LAN 无账号发现 | 真机响应 | 成功；发现不会返回设备密码 |
| AP 热点内无账号取流 | 真机 HLP 捕获、独立重组及像素解码 | 成功解码 14 帧 640×480 JPEG；另收到 4 个音频帧，本项未重新解码音频 |
| AP 热点配网 | 真机 HTTP / HLP、APP 调用路径 | 无账号下发 Wi-Fi 曾成功，摄像头入网后认证未通过 |
| BLE | APK 路径、一次真机 GATT 服务发现 | 发现 FFF0 服务 / FFF1 特征；完整配网未成功 |
| 镜头扫描 Wi-Fi 二维码 | APK 静态路径 | 未证明这台设备支持 |

AP 模式使用 `@MC-` 前缀热点，BLE 名称可不同。已观察到 AP 与 LAN 的设备标识变化，不能在切网后直接假定 ID 和凭据仍然有效。

默认凭据在 AP 控制查询及上述开流验证通过；多种本地设密尝试都没有在新连接中验证成功。包含本地生成非零 app_id 的尝试也未解决。原生 SDK 对照写入返回成功，只能证明命令被交给 SDK，不能证明摄像头应用了新密码。另一次 HTTP 设密返回 404。

2026-10-11 的普通重启命令返回成功。之后 BLE 广播在重启适配器后重新出现，但 GATT 连接报 133，底层原因是连接建立失败；错误发生在认证或 Wi-Fi 查询之前，不能用来判断配网协议是否正确。没有完成 BLE 写入验证。

**缺口：首次所有权 / 设备凭据建立，以及从 AP 转 LAN 后的新会话认证。** 在重新连接成功且收到实际媒体前，不能将无账号配对标为完成。不可向用户承诺“重置后默认密码直接接入”。

## 同版本固件的新证据

OTA 文件 659424 字节，SHA-256 为 `d056974be6ba1176db7929b5c0c5c8defaafb7bee8097d231cc7fc4b93d839de`。解包后 1111392 字节，SHA-256 为 `cc2ad73144c5f61062be7cc4c465766a35c200ec4274006ccb1339620f460749`。目录长度 / MD5、RBL 包头 / 载荷 CRC、解包长度 / FNV 均一致。这是离线分析，没有刷入设备；校验一致也不是厂商数字签名。

ARM 向量表及字符串引用支持加载基址 0x10000。以下是 Ghidra / Capstone 静态观察，结合前述真机结果理解，不能单凭反编译认定所有替代方法都不可能。

| 地址 | 观察及影响 |
| --- | --- |
| 0x37100 | CGI 分发器没有 APP 使用的 `set_users.cgi` 和 `set_ipc_binding_info.cgi`；未匹配请求直接返回，与设密无回执吻合 |
| 0x479f8 | 校验 admin 和已保存设备密码；默认密码分支受内部模式限制，与 AP 能登录、入网后拒绝吻合 |
| 0x4a0bc | Wi-Fi 配置读取 SSID、WPA 密码、area 及初始模式下的 userid，没有读取新的设备密码字段 |
| 0x3f7ac | 厂商绑定响应处理器读取 `password` 并持久化为 `app_pwd`；这是已定位到的设备密码写入路径 |
| 0x47f08 | `onvif_support_enable` 固定返回 0；`IsFactoryMode` 固定返回 1，后者不能作为实际复位状态判据 |

APP 的普通 AP 配网随后调用 `mqttBindIPCDevice` → `bindIPCDevice`，带账号认证 POST `/v3/add` 或 `/device/v3/add`。BKTMP 的 VUID 预分配属于另一分支。当前固件上，直接复用 APP 的通用本地设密命令不能完成无账号入网；没有验证本地模拟厂商服务或修改固件路线。

AP 取流测试使用独立 Node 协议生成和重组，3399 仅临时提供 Wi-Fi / UDP 收发；没有使用账号、APP 或原厂 SDK。研究过程中另访问了厂商固件目录和下载服务器，只发送公共版本信息，不能把整个研究会话描述成没有任何外网请求。

### 第二轮交叉分析：本地服务候选

APP 的设备密码在客户端随机生成，再经云绑定流程下发；不是已证明只有云端能产生密码。APP 和固件的普通 BLE 配网字段逐项一致，总长 136 字节，只有用户 ID、SSID、Wi-Fi 密码和地区，没有设备访问密码。当前固件接收上限也排除了 APP 中 368 字节的 VUID 扩展。

固件的绑定响应由独立 TCP 收发和分发器进入密码保存处理器；在已检查的调用链中，设备密码保存不以 uid 匹配成功为前提。普通 HTTP 引导会选择后续 TCP 服务器，且可能缓存数字 IP。因此可以研究只对自有摄像头做 DNS / 目的 NAT 重定向，由本地服务完成凭据建立；这仍缺正确的服务实现和真机认证证据。

另发现 SD 工厂测试文件可指定服务地址，但其模式存在升级文件扫描和运行行为变化，不作为普通用户的必需步骤。初始 AP 配网还会重建持久化环境，可能清除此前设置的设备密码，实验需先保存 WLAN 再建立凭据。

以上来自 Ghidra / Capstone 静态分析及独立格式模型的离线检查，没有实际执行本地替代绑定，也没有新取得断网冷启动结果。可选产品路径见 [接入方式](../connection-modes.md)，路由条件见 [单设备路由方案](../router-routing.md)。

后续已实现 [本地绑定服务](../local-binding-service.md)，并通过模拟客户端回环验证。引导请求是 `did`、`code` 及 AES-CBC 后 Base64 的 `did_code`；响应顶层包含 `token` 和加密 `IP_domain_port_fourth`，该固件只检查第四段存在。TCP 事件 1 登记携带真实设备 ID、code、token、uid 和版本；事件 2 的 challenge 长度须小于 8，设备依次返回 `allow` 和事件 3 的绑定请求，服务才返回设备密码。此往返对应 `0x42aa0`、`0x3f39c`、`0x3f64c`、`0x3f554`、`0x3f60c`、`0x3f7ac`。模拟验证未执行固件，不能代替真机确认。

## 初次配置需要无线适配器吗

执行 AP 配网的设备需要 Wi-Fi；执行 BLE 配网的设备需要蓝牙。它可以是用户手机或临时配置工具，不必是运行 HAOS / Frigate 的主机。相机加入家庭 Wi-Fi 后，有线主机可以直接在 LAN 上取流。

手机辅助配网是计划，尚未实现。普通网页不能直接完成原始 UDP 通信，因此不能把浏览器页面当作已解决的 AP 配网助手。
